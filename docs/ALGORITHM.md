# TaxyRay 金额与估算算法

算法版本：2（0.2.1 增加整单优惠分摊 税额舍入公式保持不变）。币种：人民币（CNY）。本工具将用户确认的含税实付金额，按用户选定的税率进行数学拆分。税率的适用性与商户应纳税额见 [税务口径](TAX_POLICY.md)。

本文包含 0.3.2（2026-09-17）的多账单录入、明确补拍与重复检查规则。这些规则只整理待确认草稿，不改变税额公式或已保存账单。

## 输入、单位与范围

| 字段 | 对外形式 | 内部形式 | 边界 |
| --- | --- | --- | --- |
| 实付金额 | 十进制元字符串，如 `"113.00"` | `Long` 分，如 `11300` | `0.00` 至 `99999999.99` 元，最多两位小数 |
| 票面实付合计 | 十进制元字符串 | `Long` 分 | `0.00` 至 `99999999990.00` 元；上限为最大单项乘以 1000 |
| 估算税率 | 百分比数值字符串，如 `"13"` | `Int` 基点，如 `1300` | `0` 至 `100`%，百分比最多两位小数 |
| 账单品目 | `List<DraftItem>` | `List<CalculatedItem>` | 每单 1 至 1000 项，编号非空且唯一 |

一个基点等于 `0.01` 个百分点。因此 `"0.13"` 表示 **0.13%**；传入 13% 必须使用 `"13"`。接口不接受百分号、千位分隔符、货币符号、指数写法、NaN、负数及超过两位的小数。前后空白和前导零允许，整个输入最多 32 个字符。过量小数明确报错，不暗中截断或舍入原始支付金额。零元赠品和全额优惠后的商品允许保留，其税前金额与税额均为零。空白金额不能当作零。退款不属于本版本的消费记录范围。

输入通过 `BigDecimal(String)` 解析，`movePointRight(2)` 后精确转换为分或基点。金额的解析、计算、持久化、汇总、导出均不得经过 `Float` / `Double`。UI 动画或绘图坐标若使用浮点数，不得反向成为账本数据来源。

## 每项只舍入税额一次

设实付金额为 `A`，税率小数为 `r`：

```text
精确税额 = A × r / (1 + r)
展示税额 = ROUND_HALF_UP(精确税额, 2 位小数)
展示税前金额 = A - 展示税额
```

代码在分单位直接计算，以 `B` 表示税率基点：

```text
taxCents = ROUND_HALF_UP(amountCents × B / (10000 + B), 0 位小数)
preTaxCents = amountCents - taxCents
```

分子用 `BigDecimal` 精确相乘；除法直接指定最终精度与 `HALF_UP`。没有先求近似商、先舍入税前金额、再求税额的中间舍入。`Long` 只保存已经确定的整数分。

| 实付 | 税率 | 税额 | 税前金额 |
| ---: | ---: | ---: | ---: |
| ¥113.00 | 13% | ¥13.00 | ¥100.00 |
| ¥109.00 | 9% | ¥9.00 | ¥100.00 |
| ¥35.00 | 13% | ¥4.03 | ¥30.97 |
| ¥106.25 | 6.25% | ¥6.25 | ¥100.00 |
| ¥0.01 | 0% | ¥0.00 | ¥0.01 |
| ¥0.01 | 100% | ¥0.01 | ¥0.00 |

最后一行是必要的半分边界：精确税额与精确税前金额各为 ¥0.005。若两者分别 `HALF_UP`，会各变成 ¥0.01，合计 ¥0.02，凭空多出一分钱。TaxyRay 优先舍入税额，税前金额取差，始终满足：

```text
amountCents == preTaxCents + taxCents
```

因此本工具显示的税前金额是与舍入税额配平后的金额。在恰好半分时，它可能与独立对 `A / (1+r)` 进行 `HALF_UP` 的结果相差一分。这是明确的产品估算口径，不宣称复刻所有开票系统的舍入方式。极小金额下舍入后的税额占实付比例可能高于 `r/(1+r)`，例如一分钱、100% 的例子占比为 100%；程序保留真实的舍入结果，不隐藏或修改它。

## 逐项汇总与有效税负率

每项独立计算完成后，再累加整数分。整单不重新算税；也不对税率做简单平均后套用整单公式。

两项各 ¥0.04、税率均 13%：每项税额约 ¥0.004602，分别舍入为 ¥0.00，整单税额为 ¥0.00。若把 ¥0.08 合并计算，会得到 ¥0.01，与逐项规则不同。按原票品目粒度输入，不任意合并或拆分明细。整单优惠先完成下面的实付分摊，再逐项计税；AI 不得猜测折扣分配或把折扣重复扣减。

```text
累计实付 = Σ 每项实付分
累计税额 = Σ 每项已舍入税额分
累计税前 = Σ 每项税前分
有效税负率 = ROUND_HALF_UP(累计税额 / 累计实付 × 100, 2 位小数)
```

分母使用含税实付。例如 ¥113、13% 档位，估算税额 ¥13，有效税负率显示 **11.50%**。有效税负率只用于展示，不能当作税率回填。空账本的 `0 / 0` 展示 `0.00%`；税额与总额的非法组合直接报错。

每单最大实付为 `9,999,999,999,000` 分，处于 `Long` 精确范围内。单据汇总使用 `Math.addExact`，溢出失败而非回绕。格式化使用 `BigDecimal`，不受设备地区的小数逗号或分组符影响。

## 整单优惠与抹零

先录入已经扣除单品优惠的商品行金额。称重商品采用票面行小计，不用数量乘单价重新计算。输入最终实付后，只有用户点击“按实付分摊优惠”才执行分摊；一分差额也不会自动忽略。实付高于商品合计时继续拦截，应先补齐漏项、附加费用或修正识别金额。

设商品金额为整数分 `a_i`，合计 `S`，用户确认的实付为 `P`，要求 `0 ≤ P ≤ S`。对分摊后的实付使用最大余数法：

```text
每项基础实付 q_i = floor(a_i × P / S)
每项余数     r_i = (a_i × P) mod S
待补分数     R   = P - Σq_i
```

按 `r_i` 从大到小选前 `R` 项，每项加一分。余数相同按原商品行顺序，结果可复现。乘积使用 `BigInteger`，避免最大金额乘整单实付超出 Long。总额为零时直接保留零元行，不做除法。时间复杂度为 `O(n log n)`，最多 1000 项。

- 各项分摊后实付之和精确等于 `P`
- 每项实付在 `0..a_i` 之间 原本零元商品不承担付款
- 每项与精确比例值的误差小于一分
- 税率不参与金额分摊 分摊完成后各商品保留自己的税率分别计税

例如 9 项金额为 `2.68 6.82 5.20 4.16 15.88 5.41 1.85 3.33 13.91`，合计 `59.24`，实付 `59.20`。分摊后为 `2.68 6.81 5.20 4.16 15.87 5.40 1.85 3.33 13.90`。另一笔 `113.00@13% + 109.00@9%` 实付 `200.00` 时，分配为 `101.80 + 98.20`，税额分别为 `11.71 + 8.11`。

表单保留分摊前金额和确认时的金额快照，可撤销。重复点击始终基于原输入，不能重复扣减。金额、商品增删、顺序或实付改变后旧快照无效，重新确认分摊；仅税率改变可在相同实付上重新计算。入账持久化的是最终逐项实付金额，重新编辑及备份使用这些已结算金额，不再次扣优惠。账本结构不增加折扣负数行。

只有部分商品参与优惠时，应直接修正对应商品金额，不使用整单比例分摊。票面已经按会员价列示商品且合计等于实付时，无需分摊，汇总优惠不能再减一次。支付渠道补贴、积分和发票折扣可能存在不同的税务口径，此处仅是用户确认后的消费端分摊约定，不用于认定商家的法定销售额。[税务机关关于折扣列示的说明](https://shanxi.chinatax.gov.cn/hdjl/zxbjxq/sx-11400-519-54734)

## 连续录入与商品重复检查

每轮最多 5 张图片通过一次 `parse_bill_batch` 工具调用返回 `VisionBatch`，其中最多 30 笔独立账单、合计最多 1000 个商品项。每笔有自己的 `ReceiptScanSession` 和核对草稿；本次列表累计最多 100 笔。不同订单保持边界，不能因为同店同价就合并。部分内容不可读时保留其他可读账单，并通过批次警告说明遗漏范围；协议或金额结构无效则拒绝本轮。

“继续选图”默认新增独立账单。只有用户在指定账单上选择“补拍这笔”，且补拍结果只有一笔时，才尝试追加到该笔 `ReceiptScanSession`；补拍返回多笔时分别作为新账单保留，原账单不变，并提示检查重复。已修改或完成的账单不再补拍。单笔每轮追加商品前检查累计数量，去重前最多 1000 项。新轮为商品重新分配 ID，防止模型或调用方复用 ID 导致覆盖；ID 不是商品重复的证据。追加失败不修改已成功的轮次。

明确补拍时，商户经 Unicode NFKC 规范化，忽略空白与大小写后比较；账单消费日期与时间按年月日时分比较。不同的已知商户或消费分钟会拒绝追加到指定账单，缺失字段可以采用该账单其他轮的已知值。同一分钟内秒数不同不构成冲突，最终采用最早识别到的有效账单时间；所有轮次都缺少时间时采用本次录入开始时间并提示用户修改，不能把截图手机状态栏时间当作消费时间。各轮提示附带识别轮次，避免“第 N 项”被误当作合并后的序号。

同一账单补拍的商品行累积，最终实付与整单优惠不累加。总额先精确转换为整数分，不同文本表示的同一数额合并为一个值。优惠按金额分去重，相同金额采用第一次识别的账单摘录。总额出现多个不同值时清空实付字段，优惠金额冲突时清空优惠字段；草稿要求最终实付非空，并展示冲突提示。冲突不会删除商品，也不会用商品合计或一次隐式优惠分摊替代确认。独立订单始终保留各自的实付与优惠。

每笔模型结果必须提供 `declared_total`，有明确实付则填写十进制金额，无可读实付才填写 `null`，不能省略。单商品已付款订单直接采用实付作为商品金额，已含优惠不再扣除；多商品账单保留可见行额并沿用前述显式分摊规则。`payment_status`、付款证据与来源图片编号只供草稿复核，不改变数学计算器。先用后付是支付方式，不等于未付款；明确实付正数且没有待付提示为 `paid`，实付 0 且之后才付款为 `unpaid`，无法判断为 `unknown`。

未付或付款不明不会阻止其余账单核对。`unpaid` 订单可跳过；后来已经付款时，必须明确确认并填写大于 0 的最终实付，不能把待付款的实付 0 通过优惠分摊变成已支付消费。`unknown` 也须核实并确认。同一账单补拍的付款状态冲突时改为 `unknown`，证据保留供用户核实。状态、证据、图号与未保存草稿仅在当前进程内存中；每笔只有通过表单校验并由用户“确认入账”后，才保存最终账单。结束识别不自动保存其余草稿。

核对一笔尚未处理的账单时，`ReceiptItemDuplicates.find` 只在该笔内本机生成候选组，不跨独立订单去重，规则如下：

1. 品名经 NFKC 规范化、转小写并移除空白。原始或规范化名称超过 200 字、不含汉字或字母等文字、默认占位名称不参加匹配。无法精确解析的金额不参加匹配。
2. 只比较实付金额相同的行。金额按整数分比较，税率及分类理由不参与匹配。
3. 先将规范化名称完全一致的行归组，再检查名称相似的组。名称中按顺序提取的数字与可识别单位必须一致，不把不同规格仅因文字接近而合并。
4. 相似匹配要求较短名称至少 6 个字符。设较长名称长度为 `L`，允许的插入、删除或替换次数为 `min(2, floor(L × 15 / 100))`。短到不允许一次编辑的名称只能完全一致才匹配。
5. 加入候选组时须与组内每种已有名称都满足上述条件，避免 A 接近 B、B 接近 C 就把 A 与 C 一起误判。候选及组的展示顺序按原商品顺序。

数字与单位按规范化后的文本比较，不推算单位换算或把不同数字视为等价。默认品名、不同金额或明显不同名称的重复照片可能不会触发候选提示。这个规则提供可解释的检查范围，不宣称确认了两行就是同一次购买。

每组保留原始商品供用户选择。点击“全部保留”不删除商品；点击“删除重复项”仅保留指定的一项，移除当前草稿里该组的其余项。实际购买多件时可以全部保留，应用不会暗中合并数量、求平均金额或修改税率。票面最终实付不随去重自动改写，最终仍按金额校验与显式优惠分摊规则处理。

## 累计贡献卡与相似账单

累计贡献卡直接汇总所有已保存商品的实付 税前与已舍入税额 逐档构成也累计对应税率的已保存税额 不对累计实付重新套用税率 不受账本搜索和近 30 天筛选影响 总额与各档之和使用受检整数加法 避免溢出回绕

AI 新草稿确认入账前读取本机账本 排除正在编辑的记录 只有实付合计相同才继续比较 满足下列任一条件时提示可能重复

- 商户相同 消费日期在设备当前时区下为同一天
- 商品名与逐项实付的多重集合相同 且商户相同 或同一天且至少一方商户缺失
- 单商品订单在同一天 至少一方商户缺失且另一方不冲突 品名满足下述 OCR 相似条件

文字先做 Unicode NFKC 规范化 忽略空白与大小写 商品顺序和税率修正不影响商品多重集合 每种商品的出现次数会保留 未命名商品的默认名称不能单独作为商品一致的证据

单商品 OCR 比较先复用商品重复检查中的保守编辑距离规则 长标题还允许重复规格文字 仅对长度 16 至 200 的名称比较相邻双字符集合 两侧各至少有 12 个不同双字符 Sørensen–Dice 相似度须达到 85% 全程用整数比较 数字与单位集合必须相同 重复出现的同一规格只计一次 单件包装标注如 1瓶可省略或出现 2瓶等数量变化仍不匹配 多商品订单不走这个宽松分支 不把多行合并成一行进行比较

这个规则用于提示 日常重复购买仍可明确选择仍然录入 也可返回核对 或选择保留已有账单并放弃当前草稿 不自动合并 不删除现有账单 商品行是否重复则使用前一节的独立检查 两种检查都由用户作最终决定

## API

包名为 `io.github.taxray.core`，纯 JVM 模块不依赖 Android：

```kotlin
TaxCalculator.calculate(amount: String, ratePercent: String): TaxBreakdown
TaxCalculator.calculateItems(items: List<DraftItem>): List<CalculatedItem>
TaxCalculator.parseReceiptTotal(amount: String): Long // 票面整单合计，单位为分
TaxCalculator.formatMoney(cents: Long): String // "113.00"，无 ¥
TaxCalculator.formatRate(bps: Int): String // "13" / "6.25"，无 %
TaxCalculator.effectiveRate(taxCents: Long, amountCents: Long): String // "11.50"
DiscountAllocator.allocate(originalCents: List<Long>, paidTotalCents: Long): DiscountAllocation
ReceiptItemDuplicates.find(items: List<DraftItem>): List<DuplicateItemGroup>
```

`calculateItems` 先校验整个列表，生成全新的结果列表。非法项抛 `IllegalArgumentException` 并标明行号；不会返回部分成功结果。它保留编号，去除品名与分类理由两端空白，空品名使用“消费品目”。只有用户确认后的结果才允许入库。`TaxBreakdown` 构造时校验范围与守恒；从外部备份载入的数据还须重新计算，不能只相信备份中的税额与合计。

## 验证

运行 `./gradlew :core:test`。`TaxCalculatorTest` 覆盖已知样例、两位自定义率、0/100% 边界、半分、逐项与整单差异、最大金额与 1000 项、输入拒绝、区域格式、金额守恒、精度污染及异常数据。25,000 组固定种子随机输入通过独立的 `BigInteger` 商余数算法核对：余数的两倍大于等于分母时进一分。同时遍历四个金额下从 0 至 10,000 的所有基点，检查税率递增时已舍入税额不下降。结果可复现，不依赖网络、AI 或系统时钟。

`DiscountAllocatorTest` 覆盖 4 分抹零、混合税率会员优惠、同余尾差、零元赠品、全额优惠和最大 1000 项乘积。另以 3000 组固定种子输入验证总额守恒、各项上下界及精确比例误差。应用层测试覆盖确认、撤销、重复应用、快照失效、保存后重开与 JSON / CSV 往返。
