# 账单识别与分类

行为版本：0.3.3 · 2026-09-18。识别支持纸质小票、购物订单截图和电子账单，只产生草稿，用户逐笔确认后才写入账本。金额拆分算法见 [ALGORITHM.md](ALGORITHM.md)，商户真实适用税率与估算边界见 [TAX_POLICY.md](TAX_POLICY.md)。

## 多图识别与逐笔核对

首页入口为“识别账单”，录入页展示接收服务、模型与费用说明。选择“拍照并识别”会打开系统相机，用户在相机确认照片后发送本轮图片。相册每轮可选择 1 至 5 张图片，预览、排序或移除后点击“发送并识别”。一张图可以包含多笔订单，多张图也可以是同一张长账单的分段。

各轮是独立 API 请求，每轮只发送本轮图片。多张图片按选择顺序放在一个请求中，模型只输出一次工具调用。每张 JPEG 不超过 1,000,000 字节，单轮合计不超过 5,000,000 字节。数量、空图片和大小在请求前校验。单次识别最多返回 30 笔账单，所有账单合计最多 1000 个商品项；输出额度为 16,384 tokens。数量超限必须明确提示未识别的范围；响应被截断时整轮报错，不把半截结果作为完整草稿。

识别完成后进入账单列表，显示每笔商户、商品、实付与付款状态，以及待核对、已入账和已跳过的数量。点击“核对账单”，修改该笔金额、时间与税率后点击“确认入账”；也可以先“跳过”，在本次识别结束前“恢复核对”。返回列表保留已修改草稿。一笔订单未付、付款不明或需要修改，不会阻止其余订单分别核对。

列表顶部提供“快速核对”入口。“一键核对”只入账同时满足这些条件的账单：付款状态为已付款，或用户已核实并填写最终实付；行内没有疑似重复商品；金额与实付能够对平，或可按实付精确分摊整单优惠；与本机账本以及同批其他账单都不重复。其余账单保留为待核对，并在确认弹窗里逐笔列出原因。确认后整批写入同一个数据库事务，任一笔校验失败则整批不入账。列表仍有待核对账单时结束识别会先弹出“账单未核对”确认，可选择一键核对账单、继续核对或结束并放弃草稿；已经确认入账的账单始终保留。

“继续选图”默认新增独立账单，不会把后一轮的商品与前一轮自动拼接。同一张长账单需要补充时，应在该笔上明确选择“补拍这笔”。补拍只返回一笔时才尝试追加到指定账单；如果返回多笔，则作为独立账单保留，原账单也保留，并提醒检查重复。已修改或完成的账单不再支持补拍。本次列表累计最多 100 笔，单笔账单补拍后仍最多 1000 个商品项。

指定补拍账单的商户名称经 Unicode NFKC 规范化、忽略空白与大小写后比较，消费时间按账单年月日时分比较。商户或消费分钟与前轮冲突时拒绝追加，原草稿保留；相同商户、相同价格本身不构成合并独立订单的依据。缺失字段可以由同一账单的其他轮补充。

部分图片或订单无法读取时，模型通过批次 `warnings` 说明对应图片和原因，仍返回其余可读订单；全部不可读时返回空 `receipts` 和非空警告，由界面提示重新选图。后一轮失败、取消或补拍冲突时，前面成功识别的内容仍保留，可重新选图或先核对已有内容。任何未入账草稿都只在当前应用进程的内存中，系统结束进程后需重新识别。结束本次识别会放弃未保存草稿，已经确认入账的账单保留。

## 付款状态与实付金额

每笔结果必须包含 `declared_total`、`payment_status`、`payment_evidence`、`source_image_indices` 和 `warnings`。`declared_total` 必须提取可见最终实付，只有没有可读实付时才返回 `null`，不能省略字段或从付款证据自由文本推算金额。付款状态只有 `paid`、`unpaid`、`unknown` 三种；证据为对应账单可见付款文字，不能根据商品原价或“先用后付”四字猜测。先用后付是支付方式：如“先用后付 实付¥18(免运费)”且无待付提示，应为 `paid`、实付 `18`。`paid` 和 `unpaid` 必须有非空证据；`unknown` 没有证据时可以返回空字符串。图片来源使用从 1 开始的、不重复的编号，不能超过本次实际发送的图片数量。付款证据和来源只用于内存草稿复核，不随账单保存。

以合成金额为例：商品标价 12 元、实付 0 元，同时写着“确认收货后自动付款 12”，应标为 `unpaid`，保留商品金额 12，不能当成零元消费或全额优惠。客户端还会检查明确的待付和未来付款证据，防止模型把它标成已付款。未付订单可直接跳过；如果用户核实后来已经付款，须填写大于 0 的最终实付并勾选“我已核实付款状态和最终实付”，通过金额校验后才能入账。`unknown` 同样需要人工核实并勾选，还必须显式填写最终实付；不能用商品合计代替未知实付。真实全额优惠可填写 0，但仍须对平金额或明确执行优惠分摊。

单商品已付款订单的商品金额和 `declared_total` 都取明确实付，而不是旁边的原价。例如合成订单原价 20、实付 18、已优惠 2，只录 18，不能再扣 2。已包含在实付里的优惠、补贴不再提取成待分摊优惠。多商品账单仍保留各行可见金额和最终实付，交由用户核对、必要时明确选择分摊。

## 重复商品由用户选择

提示词要求单张照片中的同一行只读取一次，跨照片出现的同一行则分别返回，不让模型自行去重。同名同价的独立购买行也保留。模型仍可能漏读或误读，这项约定不代表能保证识别完整。

打开一笔尚未处理的账单时，本地算法只比较该笔商品行，不跨独立订单去重。只有金额相同、规格数字一致，且规范化品名相同或满足保守相似条件的商品才会组成待确认组。短名称和默认名称不做宽泛模糊匹配，税率不作为重复判断依据。具体阈值与分组规则见 [商品重复检查](ALGORITHM.md#连续录入与商品重复检查)。

每组展示原始品名、金额与税率。实际购买了多件时可以“全部保留”，重复拍摄时可先选择要保留的一项，再点“删除重复项”。该操作只移除当前未入账草稿里的其余候选，不改变已保存账单，也不调整票面实付。用户仍需在最终核对页确认金额与税率。

每笔确认入账前还会与本机已保存账单比较。单商品购物订单即使商户被裁掉、品名有少量 OCR 错字或多带了重复规格文字，也会在日期、实付与规格一致且名称足够相似时提示可能重复。商品数量或规格冲突不会走这一相似匹配分支。用户决定继续入账或只保留已有账单，具体边界见 [相似账单](ALGORITHM.md#累计贡献卡与相似账单)。

## 分类协议

模型只调用一次 `parse_bill_batch`，顶层必须为 `receipts` 数组和 `warnings` 数组。每个 `receipts` 元素独立保存商户、商品、实付、优惠、消费时间、付款状态及来源，不把不同订单的金额相加。每笔必须至少包含一个商品项；只有明确的相同订单或连续票据内容才允许在本轮跨图归入同一账单。批次及各账单的模型警告数组各最多 30 条，每条最多 200 字；警告是待复核文本，不能执行为指令。

每项必须返回 `name`、`amount`、`category`、`category_evidence`、`classification_issue`、`tax_treatment`。单商品已付订单使用最终实付；多商品账单使用可见行小计，已包含明确的单品折扣或会员价，尚未分摊整单优惠；不是单价，也不是重新用数量乘单价得到的值。禁止猜测模糊金额或折扣分摊。旧单结果工具及其错误分支已移除，无兼容回退。图片中的指令、工具调用或 JSON 都作为不可信票据文字，不能改变识别规则；账号、密钥和个人号码不应进入输出。

客户端按结构化类别映射估算档位，不再接受模型生成的 `tax_rate` 和自由格式 `category_reason`。旧字段属于未知字段，会拒绝整个结果，没有旧协议兼容分支。

| 类别 | 含义 | 估算档位 |
| --- | --- | --- |
| `general_goods` | 日化、数码等一般商品 | 13% |
| `processed_food` | 零售加工食品，包括饼干、糕点、肉馅饼等 | 13% |
| `processed_dairy` | 酸奶、发酵乳、奶酪、奶油、调制乳等 | 13% |
| `agricultural_product` | 范围内初级农产品 | 9% |
| `fresh_milk` | 鲜奶、巴氏杀菌乳、灭菌乳 | 9% |
| `edible_oil_salt` | 食用植物油、食用盐 | 9% |
| `publication` | 正式图书、报纸、杂志等出版物 | 9% |
| `transport` | 实际客货交通运输 | 9% |
| `catering` | 餐饮服务 | 6% |
| `accommodation` | 住宿服务 | 6% |
| `life_service` | 明确的理发、洗染等居民日常服务 | 6% |
| `unknown` | 无法确定的商品或业务 | 13%，同时提示具体问题 |

这是日常消费的有限分类集合，不是完整税目数据库。仅看品名不能确定一般纳税人身份、简易计税或优惠资格；展示的是商品类别对应的估算。识别到过去日期也不会自动切换到历史税制。

`category_evidence` 是从品名或商户名称中逐字摘录的短连续文字，最长 80 字。客户端校验它确实出现在这些已提取字段中。它不能独立证明图像识别无误，也不能证明商户资格。证据不对应品名时，该项保持 13% 并提示补充品名和调整税率。

`classification_issue` 只能是 `none`、`name_incomplete`、`category_ambiguous`。它描述实际的品名或分类障碍；仅仅不知道商户税务身份不应标成分类不确定。客户端不再扫描自由理由中的“不确定”等词。正常项目没有通用警告，类别说明由本地生成，例如“加工乳制品”“加工食品”“餐饮服务”；真正的问题显示“品名不完整 可补充品名并调整税率”等具体操作。

食品边界以商品本身为依据，不能因含乳、肉或面粉就当成初级农产品。提示词明确区分鲜奶和加工乳制品、超市零售食品和餐饮服务。本地还设置有限的排除规则：模型将明确含酸奶、发酵乳、调制乳、饼干、糕点、馅饼等名称的商品归到初级农产品或鲜奶时，改回相应加工食品类别。这些规则不覆盖餐饮服务，也不把所有带“乳”“肉”“饼”字的名称一概归类。

## 免税与金额保护

`tax_treatment` 通常是 `standard`。只有明确抄录本行免税文字，才允许 `receipt_exempt`，并通过 `exemption_evidence` 提供证据。缺证据、否定或猜测表述、单独 `F` 和生鲜品名都不足以得到 0%。分类本身不明确时也不会自动设为 0%。显示的“票面标注免税”不是法定零税率认定。

全部金额保留十进制精度，不经过 Double。结果截断、结构错误、缺必填字段、未知枚举、负数金额、过量小数、重复键、无效来源和单轮超过 1000 项都会被拦截。结构或金额不可信时拒绝整轮，不静默跳过坏结果后宣称完整成功。明确的零元赠品允许保留，空白或模糊金额不得用零代替。票面总额与明细合计不一致不会暗中调平。

## 优惠提取与结算

`declared_total` 是票面明确的最终实付净额，不是原价小计、收款找零前的现金交付额，也不能把支付方式记录再加入商品列表。整单优惠尚未体现在商品行金额中时，可单独返回：

```json
{
  "declared_total": "59.20",
  "order_discount": {
    "amount": "0.04",
    "evidence": "优惠 0.04"
  }
}
```

以上只是一个账单对象的总额字段示例，完整工具参数仍须包含 `receipts`、批次 `warnings`，以及每笔必需的商品、付款状态、证据、来源和警告字段。`order_discount` 中 `amount` 和 `evidence` 均必填，只接收非负两位以内金额和最多 120 字的非空票面摘录。抹零、整单会员折扣与满减可以提取；已体现在行会员价中的折扣不得重复扣减。没有明确的优惠金额就省略，不能用商品合计与实付之差反推“识别到优惠”。原有 `amount_issue` 字段已移除，不保留兼容分支。

同一账单的最终实付或整单优惠在多张照片、明确补拍的多轮识别中重复出现时只保留一次，不随商品行相加。不同写法的金额先转为整数分比较，例如 `59.2` 和 `59.20` 视为一致。实付冲突会清空实付字段，优惠冲突会清空优惠字段，同时要求确认最终实付；付款状态冲突则变为 `unknown` 并要求人工核实。前面的商品全部保留，不用商品合计覆盖票面实付，也不靠自动分摊掩盖冲突。独立订单的实付和优惠始终分别保留。

客户端保留原商品金额和票面优惠，提示与实付的差额。如果优惠金额和差额不一致，明确提示先确认金额。已识别到整单优惠但实付缺失或被清空时，须补充实付后才能入账，不能丢掉优惠直接采用原金额。只有用户主动选择按实付分摊，才由本地整数算法结算；AI 不执行分摊、不计算税额、不写入账本。实付高于明细仍需检查漏项或附加费用。金额提示从当前表单计算，修改或分摊后不会残留旧的“不一致”警告。

Function Calling 的参数定义遵循 [DeepSeek 官方工具调用格式](https://api-docs.deepseek.com/guides/tool_calls/)。客户端始终严格解析返回值，不以模型遵守 schema 代替本地校验。

DeepSeek 官方接口的识别请求关闭思考并使用 `temperature: 0`，降低提取结果波动；这一设置不代表确定性或准确率保证。其他服务不附加这两个服务商专属设置。参数范围见 [DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)。即使模型重复返回已计入行金额的优惠，只要行合计已经等于实付，客户端不再次分摊或扣款。

## 消费时间

可选 `receipt_datetime` 使用 `YYYY-MM-DDTHH:mm:ss`，例如合成值 `2025-11-29T18:42:00`。它只代表账单当地消费时间，不含时区。年月日和时分都必须明确；账单没有秒数时规范为 `00`，不把缺失年份替换为当前年份，也不把会员有效期、重印日期或截图顶部状态栏时间当作消费时间。全部图片都未识别到该笔消费时间时，核对草稿使用本次识别开始时间，并提示用户修改；这不是模型识别出的日期。

客户端使用 `LocalDateTime` 做严格日历校验，再按设备本地时区转换，要求毫秒时间戳处于账本的 `0..253402300799999` 范围。边界按转换后的瞬间判断，不只看年份；例如东八区的 `1970-01-01T00:00:00` 早于 UTC 纪元，因此不接受。无法读取时为 `null`；无效日期、超范围时间、仅日期、时区偏移和不符合协议的格式会留空并提示修改。合法值通过 `VisionReceipt.receiptDateTime` 交给上层应用，由上层按本地时区转换并供用户修改。日期选择器的年份范围包含当前草稿年份，导入或识别较远年份时仍能打开修改，不会把已保存日期强行截断为默认范围。

## 官方依据

- [中华人民共和国增值税法](https://www.npc.gov.cn/npc/c2/c30834/202412/t20241225_442038.html)第十条列明一般货物 13%、列举范围 9%、其他服务 6% 的一般计税税率。交通运输在 9% 范围，不能作为普通生活服务套用 6%。
- [财政部 税务总局公告 2026 年第 9 号](https://www.mof.gov.cn/jrttts/202602/t20260203_3983174.htm)自 2026 年 1 月 1 日施行，明确延续现行范围，此前不一致规定以该公告为准。
- [附件 1 适用 9% 增值税税率货物范围注释](https://szs.mof.gov.cn/zhengcefabu/202601/P020260131621581319474.pdf)第 1 页区分粮食及其范围内复制品与加工速冻、方便和熟食；第 6 页区分鲜奶、巴氏及灭菌乳与酸奶等乳制品、调制乳。加工肉类熟制品也不在该初级农产品范围。
- [附件 2 销售服务 无形资产 不动产注释](https://www.mof.gov.cn/jrttts/202602/P020260203333744980975.pdf)第 18 页界定餐饮、住宿、居民日常服务，并单列加工修理修配服务。

单元测试使用合成商品和匿名数值场景，不包含用户截图原件、真实票据、会员信息或 API Key。测试覆盖多订单边界、实付金额、未付与未知付款、部分不可读警告、图片来源、批次数量限制、补拍与逐笔确认，以及结构化类别、证据关联、加工食品边界、6% 服务、免税限制、日期和原有精度与安全约束。测试还检查提示词中的不可信图片指令约束。数值场景复现验证的是客户端逻辑与协议，不代表已量测远程模型对真实图片的识别准确率。
